# legacy-ppt

옛 영업 · 기획 보고서의 문법은 그대로 두고, 색 · 타이포 · 여백 · 인터랙션만 요즘 감각으로 마감한 HTML 덱을 만든다. 결과물은 키보드로 넘기는 1600×900 슬라이드 묶음 한 파일이다.

이 스타일이 존재하는 이유를 기억하면 판단이 쉬워진다. 사내 청중은 장표 상단의 거버닝 메시지만 읽고 넘기는 경우가 많고, 플랫폼 · 운영 주제라도 글보다 구성도 · 흐름도 같은 그림을 선호한다. 반대로 AI가 만든 스타트업풍 덱(큰 히어로, 아이콘 3개 카드, 보라 그라데이션)은 오히려 성의 없어 보인다. 그래서 포맷은 보수적으로, 마감은 정교하게 간다.

## 키트

이 스킬 폴더가 키트다. 아래에서 `<kit>`은 이 SKILL.md가 있는 폴더를 뜻한다.

- `assets/deck-template.html` 엔진 · CSS · 17장 예시가 모두 든 템플릿. 가상의 "ORBIT 개발 플랫폼 운영 고도화 계획"이며 모든 컴포넌트의 실제 사용 예다
- `references/components.md` 장표 유형별 마크업, JSON 설정 형식, data 속성 레퍼런스. 슬라이드를 쓰기 전에 필요한 절을 읽는다
- `references/writing.md` 거버닝 메시지 · 개조식 · 출처 쓰는 법과 피할 표현. 문구를 쓰기 전에 읽는다
- `scripts/build.js` 소스 → 게시용 조각(`.artifact.html`)과 단독 파일(`.html`). 폰트 인라인/CDN/없음 선택 (Node 18+)
- `scripts/shoot.py` 헤드리스로 슬라이드별 PNG, 6장 몽타주, 콘솔 오류, 본문 넘침을 확인 (Python + Playwright)

템플릿 없이 처음부터 다시 짜지 않는다.

## 작업 순서

### 1. 메시지부터 정한다

장표를 그리기 전에 덱 전체를 거버닝 메시지 목록으로 먼저 쓴다. 한 장에 메시지 하나, 메시지는 결론이 담긴 한 문장이다. 이 목록만 읽어도 보고가 끝나야 한다.

정해야 할 것: 청중(임원 결재, 실무 공유, 개발자 대상), 요청할 의사결정, 발표 시간(장당 1.5~2분), 쓸 수 있는 실제 수치. 수치가 없으면 지어내지 말고 사용자에게 묻거나, 예시라고 명시하고 출처 줄에 "수치는 예시"를 단다. 레포 · 로그처럼 직접 집계할 수 있는 수치는 먼저 집계한다. 요청이 명확하면 묻지 말고 바로 시작한다.

기본 골격은 표지, 목차, Executive Summary, 섹션별 간지와 본문, (요청 사항), Appendix다. 10장 이하의 짧은 덱이면 목차와 간지를 빼도 된다. 이때는 각 섹션 첫 본문 슬라이드에 `data-section`을 직접 달고, 첫 섹션 앞의 슬라이드(요약)는 브레드크럼을 손으로 쓴다(components.md 1절).

### 2. 메시지마다 장표 유형을 고른다

`references/components.md`의 카탈로그에서 메시지를 가장 직접 보여주는 유형을 고른다. 같은 유형을 연달아 쓰지 않는다.

| 메시지의 성격 | 유형 |
|---|---|
| 무엇이 무엇과 연결되나 | 시스템 구성도 (사용자 → 플랫폼 → 외부) |
| 구조와 문제 지점 | 계층 아키텍처 + 문제점 목록 (data-focus) |
| 바뀌는 것 | TO-BE 계층 아키텍처 (노드 종류: 유지 · 변경 · 신규 · 폐기, 변경점만 보기) |
| 순서와 소요 시간 | 스윔레인 흐름 + 재생 + 시간 분해 막대 |
| 물리 배치와 장애 대응 | 배포 구성도 (존, 복제 연결선, 평시/장애 토글) |
| 추세 | KPI 타일 + 막대 · 꺾은선 차트 |
| 무슨 일이 언제 | 타임라인 + 원인/대책 패널 |
| 단계별 계획 | 쉐브론 헤더 매트릭스 |
| 누가 무엇을 | 플로차트 + RACI |
| 얼마나 좋아지나, 무엇을 달라는가 | 기대효과 표(줄어드는 막대) + 요청 카드 |
| 상세 목록 | 명세 표 + 구분 필터 (Appendix) |

카탈로그에 없는 유형(경쟁사 비교 하비볼, SWOT, 전략 체계도, 간트, 조직도 등)이 필요하면 같은 토큰과 노드 규칙으로 새로 짠다. 방법은 components.md 마지막 절에 있다.

### 3. 템플릿을 복사해 슬라이드를 바꾼다

```bash
cp <kit>/assets/deck-template.html ./<name>.src.html
```

- `<title>`, `#deck-config`의 `title`(하단 바)과 `footer`(꼬리말)를 바꾼다
- 예시 `<section class="slide">`를 지우고 새로 쓴다. 엔진 `<script>`와 `<style>`은 건드리지 않는다. 새 장표에 스타일이 더 필요하면 `<style>` 끝에 덧붙인다
- 섹션은 간지 슬라이드의 `data-section`/`data-num`으로 선언한다. 목차, 간지 내용, 진행 막대 묶음, 비어 있는 브레드크럼은 엔진이 만든다
- 연결선 · 흐름 · 타임라인 · 차트 · RACI는 슬라이드 안의 `<script type="application/json" data-kind="..." data-for="대상 id">`로 선언한다. 엔진이 그린다
- id는 덱 전체에서 유일해야 한다. 슬라이드마다 접두어를 붙인다(`ctx-`, `dp-`)
- 마크업만 보고 감이 안 오면 템플릿의 해당 예시 슬라이드를 연다. 각 장표 유형은 템플릿에 실제 동작하는 예가 하나씩 있다

### 4. 빌드한다

```bash
node <kit>/scripts/build.js <name>.src.html              # Pretendard 인라인 (기본, 약 2.7MB)
node <kit>/scripts/build.js <name>.src.html --font cdn   # 웹 호스팅 · 사내망용, 수십 KB
node <kit>/scripts/build.js <name>.src.html --font none  # 시스템 폰트, 외부 요청 0건
```

인라인은 `npm pack pretendard`로 폰트를 받는다. 네트워크가 막혔으면 `--woff2 경로`로 파일을 주거나 `--font none`으로 간다. 외부 요청이 하나도 없어야 하는 폐쇄망 배포는 `--font none`만 해당한다(`cdn`은 jsDelivr와 Google Fonts를 부른다). 사내에 Pretendard가 깔려 있지 않으면 `--woff2`로 인라인하는 편이 낫다. `--out 폴더`로 결과 위치를 바꾼다.

### 5. 한 번 찍어 보고 고친다

```bash
python <kit>/scripts/shoot.py <name>.html shots --states     # macOS/Linux는 python3
```

1장은 처음 열린 상태로, 2장부터는 실제 발표처럼 넘긴 뒤 등장 모션이 끝난 상태로 찍는다. `--states`는 보기 전환 · 필터의 두 번째 상태를 따로 찍고, 연결선 그림에서 노드를 가리켰을 때 나머지 선이 흐려지는지 확인한다. 문제가 있으면 종료 코드 1.

스크립트가 자동으로 잡는 것: 콘솔 오류(`[deck]`으로 시작하면 JSON 오류나 없는 id), 본문 넘침, 제목 · 거버닝 메시지 두 줄, 머리말의 본문 침범, 연결선 강조 실패, 템플릿 예시(ORBIT) 흔적. 잡지 못하는 것은 몽타주(`shots/contact-*.png`)와 상태 샷을 눈으로 본다: 라벨 겹침, 끊기거나 엉뚱하게 꺾인 연결선, 툴팁이 가리는 글자, 본문 아래 3분의 1이 통째로 빈 장표. 고친 뒤 한 번 더 찍는다. Chromium이 없으면(`playwright install chromium`) 이 단계는 건너뛰고 레이아웃 예산(아래)을 손으로 확인한다.

### 6. 전달한다

- claude.ai처럼 Artifact 도구가 있으면 `<name>.artifact.html`을 새 아티팩트로 게시한다. 템플릿은 이미 아티팩트 규약(제목, 측면 여백, 단일 테마의 명시적 색)을 맞춰 두었다. 도구가 artifact-design 스킬을 먼저 요구하면 따른다
- 그 외에는 `<name>.html`(단독 실행 파일)을 건넨다. 웹 사이트에 올리면 `--font cdn`, 폐쇄망이면 `--font none`으로 다시 빌드한다
- 정적 사이트 폴더에 올릴 때는 `index.src.html` → `index.html`로 빌드하고, `.src.html` · `.artifact.html`은 배포 대상에서 뺀다

## 포맷 규칙 (레거시 쪽)

본문 슬라이드는 모두 같은 뼈대를 쓴다. 위치가 매번 같아야 청중이 거버닝 메시지만 훑어 읽을 수 있다.

- 상단: 브레드크럼(섹션), 명사형 제목, 거버닝 메시지 띠(연파랑 바탕, 왼쪽 사각 마커)
- 본문: 1424×550 영역 안
- 하단: `※`로 시작하는 출처 · 기준일 · 예시 표기와 조작 힌트, 꼬리말(대외비 | 조직명), 쪽번호
- 덱 단위: 표지(대외비 표시, 연도 워터마크), 목차, 간지(PART 번호, 큰 숫자, 섹션 설명, 우측 목차 반복), Executive Summary(라벨 칸 + 내용 행), Appendix

## 디자인 규칙 (최신 쪽)

색은 남색 한 계열과 강조색 하나로 끝낸다. 색이 늘어날수록 레거시 보고서가 촌스러워진다.

| 토큰 | 값 | 쓰는 곳 |
|---|---|---|
| `--ink` | #0B1F3A | 제목, 표지 · 간지 바탕, 핵심 블록, R 배지 |
| `--elec` | #2E5BE8 | 강조 하나: 핵심 수치, 신규 컴포넌트, 마지막 데이터 |
| `--soft` / `--ice` | #8FA8EE / #E9EEFC | 보조 계열, 변경 컴포넌트, 거버닝 메시지 띠 |
| `--mist` / `--line` | #F3F5F8 / #DDE2E9 | 패널, 계층 바탕 / 헤어라인 |
| `--slate` / `--steel` | #5B6779 / #98A2B3 | 보조 텍스트 / 출처 |
| `--issue` | #D2483A | 문제점 · 장애 · 미달 지표에만. 강조색으로 쓰지 않는다 |

- 서체: Pretendard 하나, 기술 표기(명령어, 버전, 타임스탬프)만 JetBrains Mono
- 굵기를 단계로 나눈다: 제목 700, 소제목 · 노드 이름 650, 라벨 600, 거버닝 메시지 500, 본문 400. PPT의 딱딱함은 대부분 굵게/보통 두 단계에서 온다
- 크기(캔버스 px): 제목 38, 거버닝 메시지 23, 소제목 21, 본문 18~20, 보조 15~17, 출처 15. 14 미만은 꼬리말에만
- 모서리: 상자 6~7px, 패널 9~10px, 칩 · 배지는 원형. 표지 · 간지 · 큰 블록은 각지게 둬도 된다
- 그림자는 상태 강조(hover, 승격)에만 쓴다. 그라데이션은 꺾은선 아래 면에만
- 표 머리행은 남색 채움 대신 굵은 글씨 + 남색 1.5px 밑줄

## 가독성 규칙

"구성은 좋은데 PPT 특유의 딱딱하고 안 읽히는 느낌"을 만드는 원인과 처방:

- 행간: 본문 1.5 이상. 개조식 항목 사이 간격을 둔다
- 진한 면 줄이기: 남색 채움은 표지 · 간지 · 핵심 블록 · 단계 헤더에만. 라벨 칸은 연회색
- 한 블록에 항목 2~4개, 한 줄 40자 안팎. 넘치면 장을 나누거나 표로 바꾼다
- 숫자는 단위와 함께, 비교 대상과 함께("18분 (1년 새 2배)")
- 강조는 장당 두세 군데. 거버닝 메시지의 핵심 수치 하나는 반드시 강조한다
- 빈 곳을 억지로 채우지 않는다. 다만 본문 영역 아래쪽 3분의 1이 통째로 비면 레이아웃을 다시 짠다

## 그림 문법

아키텍처 그림은 슬라이드를 넘겨도 같은 의미를 유지해야 한다. AS-IS와 TO-BE를 같은 계층 격자 위에 그리고, 노드 종류의 색을 요약 · 표 · 범례까지 같게 쓴다.

- 노드 종류: `keep` 흰 바탕 회색 테두리, `change` 연파랑 + 파랑 테두리, `new` 파랑 채움, `ext` 점선(외부 시스템 · 폐기 예정), `muted` 연회색(사용자 · 종료), `core` 남색(플랫폼 본체, 결정 주체), `issue` 빨간 테두리. DB · 스토리지는 `db`(원통)
- 배지: 문제점은 빨간 원 번호, TO-BE에서 해소 표시는 파란 원 번호에 `data-tip`
- 연결선: 주 흐름은 남색 실선 화살표, 복제 · 비동기 · 전환 경로는 회색 점선(`soft`), 양방향은 `both`. 라벨은 선 위 흰 칩
- 연결선은 엔진이 노드 위치를 읽어 계산하므로, 노드를 옮기면 선이 따라온다. 좌표를 손으로 그리지 않는다

## 인터랙션 원칙

인터랙션은 그 그림이 원래 말하려던 것을 직접 보여줄 때만 넣는다. 장식용 효과를 더하면 바로 AI 덱처럼 보인다.

- 좋은 예: 문제점 항목을 가리키면 그림 위치가 강조됨, 평시/장애 토글, 흐름 재생, 차트 툴팁, 변경점만 보기, 표 필터
- 처음 열린 화면은 완성 상태여야 한다. 등장 모션은 첫 이동 뒤에만 켜진다(엔진이 처리). 썸네일과 인쇄용 캡처가 빈 화면이 되지 않게 하기 위해서다
- 조작이 숨어 있으면 출처 줄 끝에 한 줄 힌트를 단다("박스에 마우스를 올리면 연결이 표시됨")
- 숫자 올라가기(`data-count`)는 KPI 타일 같은 주인공 수치에만

## 레이아웃 예산

본문 영역은 1424×550이다(top 248, bottom 102). 넘치면 출처 줄을 덮는다. 자주 쓰는 높이:

- 툴바(토글 · 범례) 36, 소제목(`.h3`) 약 27, 블록 사이 14~30
- 계층 아키텍처: 계층 5개 기준 높이 합 480 안팎 + 간격 40
- 스윔레인: 레인 5개 × 80 = 400, 위 툴바, 아래 시간 막대 42
- 절대 배치 그림(배포 구성도, 플로차트): 컨테이너 높이를 직접 지정하고 그 안에서 좌표를 잡는다. 박스 크기는 border-box라 지정한 폭이 그대로다

## 자주 터지는 문제

- 새 CSS 클래스 이름이 템플릿 전역 이름과 겹치면 엉뚱한 스타일이 먹는다. 차트 SVG(`.bar`, `.line`, `.area`, `.pt`)와 겹치면 width/height가 도형에 들어가고, `.tip`은 전역 absolute · 투명이라 요소가 사라진다. 새 클래스에는 장표 접두어를 붙인다. 겹치기 쉬운 이름 목록은 components.md 16절
- 새 장표에 등장 모션을 걸 때 fill-mode를 `both`/`forwards`로 쓰면 끝난 뒤에도 opacity가 고정돼 hover 강조 · 보기 전환이 안 먹는다. `backwards`로 쓴다
- 노드 종류 클래스(`core`, `new`, `change`, `ext`, `muted`, `db`, `issue`)를 다른 용도로 쓰지 않는다
- JSON 블록은 큰따옴표 JSON이어야 한다. 라벨 안 따옴표는 `\"`로 쓴다. 틀리면 콘솔에 `[deck] JSON 오류`가 남고 그 그림만 빠진다
- 한 슬라이드에 보기 전환(`data-view-target`)은 하나만. `data-when` 요소는 슬라이드 범위에서 바뀐다
- 연결선 기준점은 레이아웃 좌표로 잰다. 노드의 조상에 transform을 걸지 않는다(등장 모션은 예외)
- 템플릿의 예시 수치 · 고유명사를 지우지 않고 남기는 실수가 잦다. shoot.py가 "ORBIT"은 잡지만, 그 밖의 흔적은 빌드 전에 `grep -nE "ORBIT|Jenkins|Gerrit|IR-2609|개발플랫폼"`으로 찾는다(새 덱 주제에 원래 있는 이름이면 무시)
